# WORKFLOW-CHANGED-ELSEWHERE-CONFLICT-PROTECTION-1 — outcome

**Status: complete (local commits, not pushed). 2026-08-04.**
Durable contract: [`docs/rules/workflow-revision-concurrency.md`](../../rules/workflow-revision-concurrency.md).

Ordinary workflow-builder saves used a last-write-wins UPDATE: with the same
workflow open in two tabs/browsers/devices/member sessions, the second (stale)
save silently erased the first — HTTP 200, no warning. This slice made every
authoritative definition save an atomic compare-and-swap and added the shared
"changed elsewhere" recovery experience.

## Phase 1 — reproduction (real dev DB, pre-fix tree)

Reproduced through the REAL repository functions and the REAL
`PATCH /api/workflows/[id]` handler against chainreact-dev
(`tests/integration/features/workflow-save-revision-conflict.dev.test.ts`,
first written with pre-fix assertions; captured 2026-08-04):

- workflow `b57447a0-5163-401c-83bb-3bea785e70a6`, account
  `f75cd7fb-1d95-46a2-9bae-982ebf06956d` (throwaway fixture, cleaned up).
- Sessions A and B both loaded revision `2026-08-05T02:40:03.918364+00:00`.
- A saved (`change-A`) → row advanced to `…04.269207`.
- B saved its stale edit (`change-B`) → **HTTP 200**, row `…04.335853`,
  `change-A` silently gone. Same result at the raw repository boundary
  (predicate: `.eq("id", …)` only) and the route boundary (request contract
  had NO revision field at all).
- The existing guarded primitive (`updateDraftDefinitionIfRevisionMatches`,
  AI apply) already rejected the same stale write and proved atomic (4
  concurrent CAS attempts → exactly 1 winner).

**Root-cause classification (brief's list):** #1 the save request carried no
expected revision, #2 the client HAD the token (`hydratedRevision`) but never
sent it, #5 the repository's `updateDraftDefinition` was unconditional, #6 the
predicate checked only workflow id (+ RLS account), #8 different save paths
used different concurrency rules (AI apply guarded; PATCH / template replace /
checkpoint restore unguarded). Additionally, an external strictly-newer
re-hydrate silently REPLACED a dirty draft (client-side data loss, graphSlice
hydrate).

## Phase 3 — revision-field inventory

| Field | Type | Generated by | Stored | Meaning | Suitable as the save token? |
|---|---|---|---|---|---|
| `workflows.updated_at` / `updatedAt` | timestamptz (µs) | DB trigger `set_updated_at` (`now()`) | workflows row | row revision | **YES — canonical** (proven by AI apply; PostgREST string round-trips exactly) |
| `graphSlice.hydratedRevision` | string | server (adopted client-side) | builder memory | the session's loaded revision | carrier of the canonical token |
| `computeEditableGraphVersion` | 8-hex fingerprint | pure content hash | ephemeral | draft CONTENT identity (proposal freshness; rebase equality check) | no — different space (see RESTORED-EDIT-PROPOSAL-STALE-MISMATCH-1) |
| `patch.baseRevision` | string | client echo of `updatedAt` | AI patch | AI apply's expected revision | same token, existing consumer |
| `active_revision_id` / `workflow_revisions.id` | uuid | publish flow | workflows / revisions | published immutable snapshot pointer | no — publish lineage, not draft revision |
| `created_at` | timestamptz | DB | rows | creation time | no |

No migration was required (schema already supports atomic optimistic locking);
none was created. `updated_at` precision (microseconds, trigger-stamped) is
sufficient: equality is byte-exact on the echoed wire string, and the CAS makes
write-time enforcement atomic regardless of read-time timing.

## Implementation summary

- **Contract:** `UpdateWorkflowRequestSchema` requires `expectedRevision`
  whenever `draftDefinition` is present. Replace/restore bodies require it too.
- **Repository:** `updateDraftDefinitionIfRevisionMatches` is the only
  definition writer — one atomic UPDATE on `(id, account_id, updated_at)`.
- **Service:** `saveDraftDefinition` unchanged in shape (guarded write first;
  deactivation only after a landed write) + new `classifyStaleDraftWrite`
  (no-leak conflict-vs-404 classification).
- **Routes:** PATCH runs the definition CAS BEFORE the name write (a
  same-request rename can no longer invalidate the token), read-time fast-fail,
  typed 409 via `workflowRevisionConflictResponse` (+ safe structured
  diagnostic `workflow.save.revision_conflict`). Same for replace/restore.
- **Client:** typed `WorkflowRevisionConflictError`; `graphSlice` sends the
  token, records `conflict` (edits preserved, no auto-hydrate, no 409 loop),
  transparently rebases metadata-only bumps (single retry with the latest
  token), distinguishes external vs explicit hydrates, and exposes
  `reloadLatest`/`flagConflict`. `WorkflowConflictDialog` + persistent banner
  is the one recovery experience (no force-overwrite; no auto-merge;
  save-as-copy deferred — no safe duplication path exists today).
- **Mobile contracts:** `WORKFLOW_REVISION_CONFLICT` reserved for parity.

Console: the only Tab B error is the browser's own 409 network log (expected).
Screenshots + `cert-result.json` in the session scratchpad.

**Scenario B (two members): blocked at browser level** — personal accounts
reject non-owner memberships (`account_memberships_personal_invariant_violation`)
and standing up a team account requires billing flows. Covered at
service/route/DB level instead: the CAS predicate is member-agnostic
(`account_id`-scoped), and the dev-DB suite exercises the same code path any
member session uses.

**Scenario C (builder vs React Apply): covered at unit/service level** — the
ai/apply route's read-time `baseRevision` check + the same CAS
(`applyWorkflowPatch.test.ts` STALE_PATCH cases) and client proposal freshness
(fingerprint) tests; a live browser pass would require model calls/credits.

**Scenario D (template replace vs concurrent save): covered at route/service
level** — stale replace → typed 409 before any side effect
(`templateReplace.test.ts`, `template-from-builder-routes.test.ts`); no
lifecycle/trigger effect on conflict is asserted there and guaranteed by
write-first ordering.
