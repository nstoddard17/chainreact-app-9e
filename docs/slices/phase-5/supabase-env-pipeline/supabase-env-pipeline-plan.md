## 4. Branch and promotion model

```text
Local v2-main commit
→ local verification (tsc, lint, lint:structure, lint:migrations, focused jest,
  local supabase reset when schema changed)
→ Marcus approves the exact SHA for hosted development
→ push that SHA to v2-dev (deployment marker branch)
→ deploy-development workflow (GitHub Environment: development):
    Database CI gate → link to dev project → migration dry-run → apply →
    history + schema verification → Vercel dev deployment → authenticated dev smoke
→ development certification artifact for that SHA
→ Marcus accepts in the dev app
→ Marcus approves the SAME SHA for production
→ promote-production workflow (GitHub Environment: production, manual approval):
    exact-SHA certification proof required → link to prod project →
    migration dry-run → history-divergence check → destructive-migration
    backup confirmation → apply pending forward migrations → verify →
    production app deployment → production smoke → sanitized promotion report
```

Hard rules:

- **A different SHA is never promoted because it is newer.** The promote workflow
  verifies the requested SHA has a matching development certification artifact and
  refuses otherwise.
- `v2-dev` is a deployment **marker**, not a development branch. Local work stays
  on `v2-main` (per owner's standing workflow). `v2-dev` receives only
  Marcus-approved SHAs and may be force-moved backwards only by Marcus.
- Pushing `v2-dev` and every workflow execution remain owner-gated; nothing in
  this batch pushed anything or executed a deployment.

## 5. Migration policy

- SQL files in `supabase/migrations/` are the schema source of truth.
- **Never edit an applied migration** (the 3 historical edits in §2 predate this
  rule's enforcement; a new guard test now fails CI when a tracked migration file
  is modified rather than added).
- Dashboard schema changes are prohibited; if one ever happens in an emergency it
  must be captured immediately as a forward migration.
- Production is **forward-only**; no down migrations; `migration repair` is an
  exceptional documented recovery, never a pipeline step, and is textually banned
  from the promote workflow (guard-tested).
- Breaking changes use **expand → compatible deploy → backfill → contract** across
  releases; application rollback must remain possible after any single migration
  wherever practical.
- Destructive migrations (DROP TABLE/COLUMN, data-destroying UPDATE/DELETE) require
  the promote workflow's `backup_confirmed` input and explicit owner approval.

## 6. Security policy (carried forward, now environment-aware)

- RLS + same-migration policies + explicit grants: unchanged
  (`docs/rules/database-security.md`, `npm run lint:migrations`).
- Service-role client only via `repositories/supabase/serviceRoleClient.ts`.
- Tokens/secrets encrypted with `TOKEN_ENCRYPTION_KEY` before write; **development
  and production use different keys**; encrypted prod values are never copied to dev.
- CI/deploy secrets live in GitHub **Environments** `development` and `production`
  (production requires reviewers). Workflow logs print project refs and hostnames
  only — never keys, passwords, or connection strings.
- Browser-exposed vars are the `NEXT_PUBLIC_*` allowlist; service-role and DB
  credentials must never carry that prefix (structure tests already scan bundles).

## 7. Data policy

- **No production data in development, ever** — no users, tokens, workflow
  payloads, webhook bodies, Stripe customers, or provider credentials.
- `supabase/seed.sql` is data-only (no DDL — guard-tested), deterministic,
  commit-safe, and contains only obviously-synthetic values (`*.chainreact.test`
  addresses, `SYNTHETIC-` markers). It seeds nothing auth-dependent.
- Auth-dependent fixtures (users → accounts → memberships → sample workflows) come
  from `scripts/dev-bootstrap.mjs` via the supported `auth.admin` API — never raw
  inserts into `auth.users`. The script is target-guarded (§3) and idempotent.
- Encrypted-credential columns are never seeded — dev integrations connect through
  the real OAuth flow against dev provider apps, or stay unconnected.
