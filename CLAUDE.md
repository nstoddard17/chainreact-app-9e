## V2 Architecture Boundaries

Keep provider-specific logic under:

`integrations/<provider>/`

Keep shared provider-family helpers under:

`integrations/_shared/<family>/`

Examples:

`integrations/_shared/google/`
`integrations/_shared/microsoft/`

Keep reusable trigger infrastructure under:

`services/triggers/`

Keep cron orchestration under:

`services/cron/`

Keep repositories under:

`repositories/`

Keep pure helpers only in `core/`.

**Do not import repositories or services into `core/`.**

E2E tests should use real V2 internals and mock only the external provider boundary.

**Real:**

- auth
- OAuth dispatcher/state
- token encryption

- workflow create/activate

- action handlers

**Mock:**

- Slack / Google / Microsoft / other provider network APIs

## Important Defaults

- Do not add DB migrations unless truly needed.
- Prefer existing `trigger_resources.config` for provider-specific watch/polling metadata when safe.
- Use DB-backed dedup, not in-memory dedup.
- Use `refreshAndRetry` for provider API calls that can receive 401.
- Use Q-contract helpers where applicable.
- Keep manifest capabilities honest. Do not set `actions: true` or `webhookTrigger: true` until handlers/triggers are actually registered.

## Deep Gotchas

### Slack message canonical eventType: `channel_type` is authoritative; `G…`-prefix fallback is intentionally dropped

`integrations/slack/webhooks/normalize.ts` derives one of four canonical
eventTypes for Slack `message` events: `slack.message.channel`,
`slack.message.group`, `slack.message.im`, `slack.message.mpim`. The
inner event's `channel_type` field is Slack's authoritative signal and
is checked first.

When `channel_type` is absent (legacy payloads, certain subtypes) the
normalizer falls back to channel-id prefix — but **only** for `C…`
(public channel) and `D…` (DM). The historical `G…`-prefix branch that
used to map to `mpim` was **removed in Slack 2.2** because the `G`
prefix is ambiguous: legacy private channels share it with group DMs
and the two cannot be disambiguated from the id alone. Such payloads
now emit generic `slack.message`, which has no registered filter — the
dispatcher drops with `matched=0`.

If you ever feel tempted to re-add a `G→mpim` (or any kind) fallback,
re-read the slice 2.2 retro doc first. Modern private channels carry
`channel_type === "group"` (often with a `C…` id); the authoritative
path resolves them cleanly.

### Slack action contract: id-only, no silent name resolution; `users:read.email` stays out by default

Every Slack action handler under [`integrations/slack/actions/`](./integrations/slack/actions/) accepts channel and user ids only:
- `channel` must match `^[CG][A-Z0-9]+$` (or `^[CDG][A-Z0-9]+$` for `get_channel_info`, which also resolves DMs).
- `user` must match `^U[A-Z0-9]+$`.

Handlers do NOT call `conversations.list` or `users.list` internally to
translate names → ids. Workflow authors that have only a name compose
`list_channels` / `list_users` upstream and select the id. V1 quietly
accepted a string-or-object union with name fallback; that path is
intentionally not ported (avoids hidden round-trips, eliminates
ambiguity when a name matches both a public and a private channel).

**`users:read.email` is permanently excluded from the Slack manifest.**
`users.info` and `users.list` work on plain `users:read`; Slack returns
`profile.email` as `null` / absent. Handlers do NOT project `email` to
top-level output — the raw `user` object is preserved so workspaces
that grant the scope externally can read `{{nodeId.user.profile.email}}`.
The V1 `findUser` (`users.lookupByEmail`) action is permanently skipped
(orphan + PII). If a workflow truly needs email-by-user-id, that's a
product decision that re-opens the scope question, not a quick port.

If you're adding a new Slack action, mirror this pattern: strict id
regex in the Zod schema, no name resolution side-effects in the
handler, no scope additions beyond what Slack's docs require for the
specific endpoint.

### Slack action folder grouping

[`integrations/slack/actions/`](./integrations/slack/actions/) is
domain-grouped to stay under the 50-file leaf-folder limit:
- `actions/channels/` — channel reads + lifecycle / admin / membership / metadata (12 actions).
- `actions/users/` — user lookups (2 actions).
- `actions/files/` — `upload_file`, `download_file`, `get_file_info` (3 actions; Slack 2.4).
- `actions/` parent — messaging, scheduling, reactions+pins, Block Kit, helpers.

New Slack actions land in the domain subfolder that matches their Slack
API namespace. Import paths in `services/execution/handlers/_registry.ts`
and test files must follow the same convention.

### Slack file actions: P-S3 enforcement specifics (Slack 2.4)

Every Slack file handler under [`integrations/slack/actions/files/`](./integrations/slack/actions/files/) consumes / produces `FileRef` exclusively. The 10 V1 rot patterns from the Slack 2.4 plan §7 (inline `content` / `base64Data` config arms, `fileSource` discriminator, `asUser` toggle, `workspace` selector, raw URL config arm, base64 outputs, logging `url_private_download`) are not ported and must not be reintroduced.

Two Slack-specific applications of the P-S3 gotcha (below) worth pinning:

- **`upload_file` rejects `FileRef(kind=provider_url)` at handler entry.** Slack 2.4 does NOT introduce a Slack-specific `providerFetcher` and does NOT extend `core/files/fetchFileBytes.ts`. Workflow authors composing `<any>:get_file_info → slack:upload_file` must materialize durable bytes first (`<any>:download_file` → `FileRef(v2_storage)` → `slack:upload_file`). A cross-provider `provider_url` fetch adapter is future platform work, not Slack 2.4 scope. Per P-S3 durable rule #5.
- **`download_file` is bot-token only.** `url_private_download` GETs attach `Authorization: Bearer ${botToken}` and nothing else. No user-token (`xoxp-…`) file scopes are in the manifest. V1's `asUser: true` toggle is not ported.

### Slack `file_shared` events use snake_case `_id`-suffixed fields, NOT bare `channel` (Slack 2.5)

Slack's `file_shared` event uses `event.file_id`, `event.user_id`, `event.channel_id` — UNLIKE the `message` event which uses bare `event.channel` and `event.user`. Trigger filters reading the wrong field silently never match. The [`fileUploaded`](./integrations/slack/triggers/fileUploaded/filter.ts) filter reads `payload.channel_id`; copy-pasting from `memberJoinedChannel` or `newMessageChannel` (which use bare `payload.channel`) is the bug-magnet. Both the unit test ([`tests/unit/integrations/slack/triggers/fileUploaded/filter.test.ts`](./tests/unit/integrations/slack/triggers/fileUploaded/filter.test.ts)) and the e2e regression guard (decoy `payload.channel` carried alongside the correct `payload.channel_id`) pin this from both angles. When adding a new Slack trigger filter, consult Slack's event docs for the exact payload key (snake_case `_id` vs bare) before reading it.

### Slack trigger filters are pure: no `files.info`, no FileRef construction, no I/O (Slack 2.5)

Slack trigger filters under [`integrations/slack/triggers/`](./integrations/slack/triggers/) are pure synchronous `parseConfig` + `evaluate` functions. They MUST NOT call `files.info` / `conversations.info` / `users.info` to enrich the payload, MUST NOT construct a `FileRef`, and MUST NOT return Promises. The trigger payload is the raw Slack inner event verbatim. Workflows that need enriched metadata or a `FileRef` compose the right action downstream (e.g. `slack.file_shared → slack:get_file_info` yields `FileRef(kind=provider_url)` + flat metadata; `slack.file_shared → slack:download_file` yields `FileRef(kind=v2_storage)` + staged bytes). V1's 17-field synthetic output schema for `fileUploaded` (`fileName`, `fileType`, `fileSize`, `fileUrl`, `userName`, `channelName`, etc.) was fiction — not in Slack's raw payload, never wired in V1 either, and not ported to V2. If a Slack trigger payload appears to be "missing" data, the answer is composition, not enrichment inside the filter.

### Token-ingest auth contract (Slice 17 — Trello pattern)

V2 ships **two** auth contracts side by side, discriminated by `ProviderManifest.authFlow`:

- `"code_callback"` (DEFAULT) — standard OAuth 2.0 code/state through `ProviderOAuth`. Every provider through Slice 16 uses this.
- `"token_ingest"` — provider returns token in URL fragment; V2 client page POSTs it to `/api/integrations/oauth/[provider]/ingest` → `dispatcher.handleTokenIngest` → server-side verify + persist. **Trello is the inaugural production consumer.**

Reach for `ProviderTokenIngestAuth` ONLY when the provider's auth flow does not surface a `code` to a server callback. If a provider has any working OAuth 2.0 code/state flow, use `ProviderOAuth` — do not "future-proof" by adopting token-ingest where it's not required. Schema invariant: `authFlow: "token_ingest"` AND `refreshable: true` is rejected at manifest load (token-ingest providers do not refresh).

Token-ingest dispatcher checks are stricter than OAuth callback in one place: **session user MUST equal state JWT's userId.** Both server hops (connect + ingest) share a browser session, so a state token POSTed by a different signed-in user is unambiguously a hijack attempt and rejected with `InvalidStateError("session/state user mismatch")`.

Full design + 12 numbered security rules: [`docs/slices/phase-1/trello-token-ingest-outcomes.md`](./docs/slices/phase-1/trello-token-ingest-outcomes.md) §3.

### `TriggerEvent.eventType` MUST match `trigger_resources.event_type` short form

**Pinned by a Slice 17 Commit 5 → Commit 6 bug.** Webhook normalizers emit a canonical `TriggerEvent`; `dispatchTriggerEvent` looks up matching workflows via `listForDispatch(provider, eventType)`. If the normalizer puts a provider-classified namespaced form (e.g. `"trello.card.created"`) into `eventType` while `trigger_resources.event_type` stores the short form (`"new_card"`, from `registerActivation("trello", "new_card", …)`), the lookup matches zero rows and workflow_runs are never created.

**Rule for every provider with a webhook trigger:**

> `TriggerEvent.eventType` MUST match the short form passed to `registerActivation(provider, eventType, …)` — the same value stored in `trigger_resources.event_type`. The provider's namespaced / classified subtype belongs in `payload.classifiedType` (or another payload field) for advanced workflow refs, NOT in the canonical `eventType` field that drives dispatch lookup.

Trello's `_shared/normalize.ts` separates the two: `triggerEventType: TrelloTriggerEventName` (short form, emitted as `TriggerEvent.eventType`) and `classifiedType: TrelloEventType` (namespaced, emitted on `payload.classifiedType`). Every other provider's normalizer should be sanity-checked against this rule when reviewed.

**Companion rule for action handlers consuming `triggerEvent.accountId`:** the `accountId` field is the **event scope** (Trello = board id; Slack = team id; etc.), NOT necessarily the integration discriminator. For `tokenScope: "user"` providers like Trello, action handlers MUST pass `accountId: null` to `refreshAndRetry` so `getActiveForExecution` returns the first active row for the user. Passing `triggerEvent.accountId` blindly will fail integration lookup when event-scope and integration-scope disagree. Slice 17 Commit 6 fixed this across all 8 Trello action handlers after the e2e exposed it.

### Gmail attachment triggers stay metadata-only; `get_attachment` is the only byte path (Gmail 2.3)

Gmail's attachment-related triggers under [`integrations/gmail/triggers/`](./integrations/gmail/triggers/) (`new_attachment`, and any future attachment-aware additions) MUST stay metadata-only at the trigger boundary. Their payload may carry `attachments[]` + `attachmentCount` (per-attachment objects with exactly `attachmentId`, `filename`, `mimeType`, `sizeBytes`), but MUST NOT include `file`, `FileRef`, `data`, `content`, `base64`, or `bytes`. Triggers that need to enumerate attachments hydrate with `usersMessagesGet({ format: "full" })` and walk `payload.parts` via the shared [`extractAttachmentMetadata`](./integrations/gmail/triggers/newAttachment/extractAttachmentMetadata.ts) (filename non-empty AND `body.attachmentId` present); the bytes endpoint (`users.messages.attachments.get`) is NOT touched at trigger time. Workflow authors who need bytes compose `gmail/get_attachment(messageId, attachmentId)` downstream — that action is the ONLY Gmail surface that materializes bytes via `stageFileToStorage` and emits `FileRef(kind=v2_storage, provider="gmail")`. The metadata stored on the `workflow_files` row is restricted to exactly `{ messageId, attachmentId }` — no email headers, no subject, no addresses, no snippets, no tokens, no PII.

V1's `downloadAttachment` action (cross-provider Drive/OneDrive/Dropbox routing inside a single 413-line handler) is folded into `get_attachment` per Gmail 2.3 plan §8 + decision §13.1. There is no `gmail:download_attachment` registry entry and no alias — the registry test asserts both `get_attachment` IS registered and `download_attachment` is NOT. V1's cross-provider upload step is replaced by composition: `gmail/get_attachment → <provider>/upload_file` consumes the FileRef. Do NOT reintroduce `download_attachment` as a separate action, an alias, or a flag on `get_attachment`. Do NOT add a `storageService` / `folderId` config field to `get_attachment`. Provider routing is the workflow's job, not the action's.

The same trigger-vs-action separation generalizes to future Gmail surfaces (and arguably to any provider where the trigger emits a thin handle and the action does the I/O). If a Gmail trigger payload "needs" file bytes, the answer is composition, not enrichment inside the trigger.

### Per-trigger Gmail dedup prefix convention (Gmail 2.3)

`webhook_event_dedup` is keyed on `(provider, eventId)`. When a single Gmail message can independently fire multiple polling triggers (`new_email`, `new_labeled_email`, `new_attachment`), each trigger's dedup wrapper prefixes the `eventId` so the same provider message id stays distinguishable across trigger types:

| Trigger | Dedup key | Wrapper |
|---|---|---|
| `new_email` | `<messageId>` (bare) | [`newEmail/dedup.ts:checkAndMarkSeen`](./integrations/gmail/triggers/newEmail/dedup.ts) |
| `new_labeled_email` | `labeled:<messageId>` | [`newLabeledEmail/dedup.ts:checkAndMarkSeenLabeled`](./integrations/gmail/triggers/newLabeledEmail/dedup.ts) |
| `new_attachment` | `attachment:<messageId>` | [`newAttachment/dedup.ts:checkAndMarkSeenAttachment`](./integrations/gmail/triggers/newAttachment/dedup.ts) |

The prefix is the dedup wrapper's responsibility — never the dispatcher's. The canonical `TriggerEvent.eventId` value uses the same prefix (`labeled:<id>` / `attachment:<id>`) so cross-trigger-type events stay distinguishable at the dispatch layer too. Any future Gmail trigger that can re-fire on the same message id MUST take a fresh prefix; don't reuse an existing one. The same convention generalizes to any provider with multiple polling triggers that fan out across the same provider entity.

### Notion Phase 2 patterns: typed-and-narrow, no kitchen-sink, no escape hatch (Notion 2.1)

Notion's V1 source is the largest single-file kitchen-sink in the V1 codebase ([`lib/workflows/actions/notion/handlers.ts`](c:/Users/marcu/source/repos/nstoddard17/chainreact-app-9e/lib/workflows/actions/notion/handlers.ts), 3,041 LOC, ~30 exported action functions in one file plus 532/613/288/140/130-LOC per-domain `manage_*` routers). V2 Notion Phase 2 deliberately does NOT recreate this shape. Four durable rules every future Notion action / wrapper / schema MUST follow:

1. **Typed actions only, one Notion endpoint per V2 action.** No `operation: string` dispatch fields. No multi-purpose routers. If a Notion endpoint needs multiple V2 ports (e.g. PATCH /v1/pages with `archived: true` vs `archived: false`), ship them as separate typed actions with hard-coded behavior — see `archivePage.ts` / `restorePage.ts` for the precedent. The Slack 2.3 / 2.4 per-action-file convention applies identically.
2. **No `make_api_call` escape hatch.** V1 ships [`notion_action_api_call`](c:/Users/marcu/source/repos/nstoddard17/chainreact-app-9e/lib/workflows/nodes/providers/notion/actions/makeApiCall.schema.ts) accepting method/path/body/headers as a generic passthrough — V2 does NOT port and does NOT introduce equivalents. Action gaps are filled by targeted typed ports tracked in [`docs/slices/parity/parity-notion.md`](./docs/slices/parity/parity-notion.md) §7.
3. **No raw Notion payload passthrough.** Schemas are `.strict()` and reject raw `rich_text` arrays, raw property wire-format objects (e.g. `{ select: { options: [...] } }`), raw block objects, and pre-built `parent: { workspace: true }` discriminators. V2 wrappers synthesize Notion's wire-format from V2-shaped inputs (`text: string` → rich_text array; `properties: Record<string, { type }>` → `{ <name>: { <type>: {} } }`). The handler synthesizes, the wrapper sends — workflow authors never see Notion's wire-format unless explicitly approved by a parity-audit decision (e.g. `queryDatabase`'s forward-passed `filter` object, which is a documented exception per Slice 9).
4. **List actions are single-page by default.** `list_users` / `list_comments` / `get_block_children` (and `queryDatabase` / `search` from Slice 9) all return exactly ONE page of results. Workflow authors compose a downstream loop on `nextCursor` + `hasMore` to walk all pages. Auto-pagination is rejected — Notion's rate limits + the runs-table size cost both argue against silent multi-page fetches inside a single action. Unit tests pin this with explicit "exactly one wrapper call when has_more is true" guards.

### Google Sheets Phase 2 patterns: typed-and-narrow, single-cell cell actions, single-row delete, equals-only find, bare-API create (Google Sheets 2.1)

Google Sheets's V1 surface ships kitchen-sink shapes across nearly every action: a 123-LOC [`unifiedAction.ts`](c:/Users/marcu/source/repos/nstoddard17/chainreact-app-9e/lib/workflows/actions/google-sheets/unifiedAction.ts) router dispatching add/update/delete via a single `config.action` field, a `deleteBy: "row_number" | "range" | "column_value"` mode dispatcher on [`deleteRow.ts`](c:/Users/marcu/source/repos/nstoddard17/chainreact-app-9e/lib/workflows/actions/google-sheets/deleteRow.ts), a 12-operator filter-and-export schema on `export_sheet` / `listRows.ts`, and a 302-LOC [`createSpreadsheet.ts`](c:/Users/marcu/source/repos/nstoddard17/chainreact-app-9e/lib/workflows/actions/googleSheets/createSpreadsheet.ts) with template chrome (budget/project/crm/inventory/calendar), CSV initialData prefill, description-as-A1-note workaround, and Drive folder placement. V2 Google Sheets Phase 2 deliberately does NOT recreate these shapes. Six durable rules every future Sheets action / wrapper / schema MUST follow:

1. **Typed actions only, one Sheets endpoint per V2 action.** No `action` / `deleteBy` / `searchColumn` discriminator fields. No multi-purpose routers. V1's `unifiedAction.ts` add/update/delete pattern is NOT ported — V2 ships separate `append_row` / `update_row` / `delete_row` typed actions. V1's `deleteRow.ts` mode dispatcher is NOT ported — `delete_row` is single-row-by-rowNumber only; range/column-value/cascade modes compose via `find_row` + multiple `delete_row` calls in descending order.

2. **Cell actions are single-cell only — A1 regex enforced.** `get_cell_value` and `update_cell` validate `cell` against `^[A-Za-z]+[0-9]+$`. Ranges (`A1:B5`), full columns (`A:A`), full rows (`1:1`), and bare letters/digits are rejected at parse time. Workflows that want range reads/writes compose `read_rows` / `update_row` / `clear_range` instead. Cell actions exist precisely to avoid the array-of-arrays output (`read_rows`) when the caller knows they want a scalar. The handler builds the A1 range as `<sheetName>!<cell>` — no implicit default sheet, no range syntax leaking into the input shape.

3. **`find_row` is equals-only, case-sensitive, header-name only in Sheets 2.1.** `operator` is `z.literal("equals")` (forward-compat enum widening; Sheets 2.2+ can add `"contains"` / `"starts_with"` / `"greater_than"` non-breakingly). `column` accepts header name only — no `*` wildcard, no single-letter shorthand. Equality is `String(cell) === String(value)` coerced (handles numeric stored as number vs string-passed value). Case-sensitivity is the floor — V1's `toLowerCase()` + `normalizeBooleanValue` heuristic (mapping yes/y/true/1/on → true) is NOT ported. Empty cells in the search column are skipped during scan. Output is uniform across single + `returnAll` modes — same key set `{found, firstMatch, matches, count}` so workflow templates don't fork.

4. **`create_spreadsheet` ships the bare `spreadsheets.create` surface only.** Just `title` (required) + `initialSheetName` (optional). Omitting `initialSheetName` sends NO `sheets[]` field and lets Google create the default `Sheet1`; providing it sends `sheets: [{ properties: { title } }]` only. No `template` chrome (budget / project / crm / inventory / calendar with hardcoded headers + sample rows). No `initialData` CSV prefill. No `description` as A1-note workaround via follow-up `batchUpdate`. No `folder` placement via secondary `drive.files.update`. No `locale` / `timeZone` overrides. No `sheetNames[]` multi-sheet array. No silent `title = "New Spreadsheet"` default. No hardcoded `gridProperties: { rowCount: 1000, columnCount: 26 }`. Multi-sheet creation and folder placement compose via downstream actions; template UX is a Phase 3 builder concern. `create_spreadsheet` is intentionally NOT wrapped in Q4 idempotency — create-shaped actions return a fresh resource on every workflow re-run, which is the right semantics.

5. **`valueInputOption` is REQUIRED on every Sheets write handler (Q11).** `update_cell` (matching Slice 5's `append_row` + `update_row`) requires `valueInputOption: "RAW" | "USER_ENTERED"` at the schema layer — no hidden default. V1's `updateCell.ts` silently defaulted to `USER_ENTERED` which surprised users when literal cell content containing `=` was parsed as a formula. V2 forces the choice.

6. **Auxiliary calls also wrap in `refreshAndRetry`.** `delete_row` composes `spreadsheetsGet` (sheetName → sheetId resolution) + `spreadsheetsBatchUpdate` (the principal write). BOTH calls go through `refreshAndRetry` — auxiliary metadata fetches that precede a write need the same token-decryption + 401 retry mediation as the write itself. Per CLAUDE.md §"OAuth 401 handling" rule.

#### Google Sheets 2.2 additions: typed `batch_update`, provider-local `format_range`, bare A1 helper, randomized e2e trigger rows

Sheets 2.2 adds `batch_update` + `format_range` on top of the Sheets 2.1 baseline. Five additional durable rules extend the patterns above:

7. **`batch_update` is typed-only — no raw `requests[]`, no JSON-string `updates`, no `cellN`/`valueN` UI chrome.** Schema accepts exactly `updates: Array<{range, values}>` where each `range` MUST include a sheet-name prefix (regex `^[^!]+!.+$` enforced at parse time, not post-hoc). Throws `InvalidA1RangeError` for: full-column refs (`A:A`), full-row refs (`1:1`), sheet-prefixed refs (`Sheet1!A1`), lowercase letters (`a1`), inverted ranges (`B2:A1`). Returns the 0-indexed half-open `GridRange` shape (`startRowIndex` inclusive / `endRowIndex` exclusive). `sheetId` is added by the caller via `spreadsheetsGet` → sheetName-resolution; the helper itself is I/O-free and unit-tested independently. V1 inlined this conversion inside `formatRange.ts:66-80`; V2 extracts it so the logic is testable without the action's I/O surface. `format_range`'s schema enforces the bare-A1 regex on the user-facing `range` field, so most rejection cases fail at parse time before reaching the helper.

10. **`format_range` builds a dynamic per-leaf `fields` mask.** Sheets' `repeatCell.fields` mask determines which sub-paths of `userEnteredFormat` Sheets OVERWRITES — paths NOT in the mask are preserved. V1 sent broad masks like `"userEnteredFormat"` or `"userEnteredFormat.textFormat"`, blowing away unrelated properties. V2 appends exactly one path per supplied option: `userEnteredFormat.backgroundColor`, `userEnteredFormat.textFormat.foregroundColor`, `userEnteredFormat.textFormat.bold`, `userEnteredFormat.textFormat.italic`, `userEnteredFormat.horizontalAlignment`, `userEnteredFormat.numberFormat`. When only `bold` is supplied, the mask is exactly `userEnteredFormat.textFormat.bold` — Sheets preserves any existing italic / strikethrough / underline / fontSize values. Insertion order is preserved (the handler appends in fixed iteration order); the e2e splits + sorts before asserting so the assertion is stable regardless of source-order shuffling.

11. **Sheets chained e2e trigger rows MUST use per-run randomized values.** V2's Google Sheets `row_changed` trigger normalizes events with a deterministic `eventId` of the form `${spreadsheetId}:${sheetName}:${rowIndex}:${sha256(JSON.stringify(values)).slice(0,12)}` (see [`integrations/google-sheets/triggers/rowChanged/normalize.ts`](./integrations/google-sheets/triggers/rowChanged/normalize.ts)). The cure is to randomize the trigger-firing row value per-run (`carol-${randomUUID()}` pattern). The slice-5b single-action test established the pattern; both Sheets 2.1 and Sheets 2.2 chained tests apply it. Documented at the spec-file level in [`tests/e2e/slice-5b-google-sheets-walkthrough.spec.ts`](./tests/e2e/slice-5b-google-sheets-walkthrough.spec.ts). #### Google Sheets 2.3 additions: bounded snapshots, two-branch pull dispatch, keyColumn opt-in, new_worksheet rides the same Drive watch

Sheets 2.3 extends `row_changed` with `updated` + `removed` change kinds via a bounded per-row hash snapshot and adds a new `new_worksheet` trigger that rides the existing Drive `files.watch` channel. Seven additional durable rules extend the Sheets Phase 2 set:

12. **`snapshotRowLimit` is the load-bearing decision; bounded window is non-negotiable.** V1 shipped `googleSheetsRowSnapshot.rowHashes` unbounded — `O(rows × workflows)` storage. Audit R-3. V2 caps the snapshot window at `snapshotRowLimit` rows (default 1,000, max 10,000) — the LAST N rows of the sheet only. `z.number().int().min(100).max(10000).default(1000)` enforces the cap at schema time; raising beyond 10,000 requires a code change, no schema escape hatch. Storage cost ≈ 80 KB per workflow trigger at default cap; the slice ships only when the bound holds. Updates to rows BEFORE the window start are silently un-tracked by design — workflow authors raise the cap or use downstream-filter strategies.

13. **Two-branch pull dispatch — Slice 5 fast path stays byte-for-byte.** [`integrations/google-sheets/triggers/rowChanged/pull.ts`](./integrations/google-sheets/triggers/rowChanged/pull.ts) branches on the workflow's `changeKinds`: default `["added"]` (or absent, for trigger rows that predate Sheets 2.3) → the legacy count-delta fast path (`lastRowCount` only, no snapshot read, no diff helpers, Slice 5 eventId format byte-for-byte). Any other value → the snapshot-diff path (reads `config.snapshot`, builds a new bounded snapshot from the current `values.get`, runs `findAdded` / `findUpdated` / `findRemoved`, persists the new snapshot). Activation seeds the snapshot ONLY when `requiresExtendedSnapshot(config)` is true — the persisted config shape stays Slice 5 byte-for-byte when `changeKinds = ["added"]` (no `snapshot` field at all, NOT `snapshot: null`). Zero migration required for legacy rows.

14. **Activation throws on overflow — `SnapshotOverflowError` aborts the activate transition.** [`_shared/snapshot.ts:buildBoundedSnapshot`](./integrations/google-sheets/triggers/_shared/snapshot.ts) throws when the sheet's data-row count exceeds `snapshotRowLimit × 2` (D-OverflowAtActivate strict reject). Activation propagates the throw → the lifecycle surfaces `TRIGGER_REGISTRATION_FAILED` → the workflow author sees the error in the builder. NOT silent truncation, NOT auto-raise. The `× 2` slack absorbs natural row-count oscillation between activation and the first webhook fire; beyond that, the author must explicitly raise the cap.

15. **Positional default + opt-in `keyColumn`; `headerRow: true` precondition enforced by `.refine`.** Default snapshot keys are 1-indexed SHEET row numbers as strings (header-inclusive numbering — sheet row 1 stays row 1 regardless of `headerRow`). Mid-sheet inserts/deletes shift positional keys so they look like `updated` + `added` / `removed` events from the diff. **Accepted limitation — same as Excel `updated_row`.** When `keyColumn` is set, the column NAME (string) is matched in the header row, its CELL VALUE per row becomes the snapshot key (coerced to string). `RowChangedInputConfigSchema.refine` rejects `keyColumn` without `headerRow: true` at parse time. `keyColumn` duplicates: last-write-wins + structured `sheets.pull.keycolumn_duplicate` warn log (NOT abort). `keyColumn` empty cells (`undefined` / `null` / `""`) are excluded from the snapshot entirely (NOT keyed as empty string). The 2.3 e2e at [`tests/e2e/slice-5b-google-sheets-walkthrough.spec.ts`](./tests/e2e/slice-5b-google-sheets-walkthrough.spec.ts) test 2 pins the contrast end-to-end: insert + update one keyed row → exactly 2 events fire (the new add + the keyed update), NO event for the shifted-but-unchanged row.

16. **Window-slide vs genuine-removal — `findRemoved` distinguishes them; keyColumn mode treats every absent key as genuine.** In POSITIONAL mode, [`_shared/snapshot.ts:findRemoved`](./integrations/google-sheets/triggers/_shared/snapshot.ts) consults the current snapshot's `windowStart` / `windowEnd` to decide: `keyNum > windowEnd` → past sheet's end → genuine removal; `keyNum < windowStart` AND `windowStart > 1` → slid out of front of window → suppress; `keyNum ∈ [windowStart, windowEnd]` AND missing → genuine in-window removal. In KEYCOLUMN mode, `isWindowSlideArtifact` returns `false` unconditionally — every previous key absent from current is a genuine removal (the row was deleted OR the keyColumn cell changed; both effectively destroy the identity). Window-slide e2e coverage was deferred to unit-only at [`tests/unit/integrations/google-sheets/triggers/_shared/snapshot.test.ts`](./tests/unit/integrations/google-sheets/triggers/_shared/snapshot.test.ts) because reproducing it from e2e requires pre-populating 200+ rows to push past `snapshotRowLimit × 2`.

17. **Event ID format branches on `changeKinds`; legacy preserved, extended carries `:changeKind:` infix.** [`integrations/google-sheets/triggers/rowChanged/normalize.ts`](./integrations/google-sheets/triggers/rowChanged/normalize.ts) builds two formats: legacy `${spreadsheetId}:${sheetName}:${rowIndex}:${hash}` (Slice 5 byte-for-byte) when `useLegacyEventId: true` (count-delta fast path); extended `${spreadsheetId}:${sheetName}:${changeKind}:${key}:${hash}` (D-EventId infix) when `useLegacyEventId: false` (snapshot-diff path). The infix prevents an `added` event for row N from colliding with a hypothetical later `updated` for that row in `webhook_event_dedup`. For `removed` events the hash component is the LAST-KNOWN pre-removal hash so the same removal fired twice dedupes naturally. `previousValues: null` is the honest placeholder per D-PreviousValues; V1's outputSchema documented `previousValues` + `changedColumns` aspirationally but the poller never computed them — V2 ships neither in real form (storage cost doubles for real `previousValues`; deferred to on-demand follow-up).

18. **`new_worksheet` rides the same Drive watch; receive route dispatches by `trigger.eventType`.** Sheets has no native push notifications for tab additions. The accepted transport (D-NewWorksheetTransport option a) is Drive `files.watch` against the spreadsheet's fileId — the same channel `row_changed` uses. Each `new_worksheet` trigger node gets its own channel (channelId = `chainreact-${node.id}-${uuid}`) so the receive route's channel-to-trigger lookup uniquely resolves the receiving trigger. [`integrations/google-sheets/webhooks/receive.ts`](./integrations/google-sheets/webhooks/receive.ts) dispatches by `trigger.eventType` (`row_changed` → `rowChangedPull`, `new_worksheet` → `newWorksheetPull`); unknown eventType → structured warn log + 200 ack. The renewal cron picks up both trigger types via the shared `type: "subscription-watch"` tag. Activation seeds `worksheetSnapshot.names` baseline so existing tabs don't fire — only worksheets created AFTER activation generate events. Rename appears as `{remove old name, add new name}` from `spreadsheets.get`'s perspective and fires ONE event for the new name (matches V1 poller + Excel). EventId carries the numeric sheetId AND a 12-char nameHash: `${spreadsheetId}:new_worksheet:${sheetId}:${nameHash}` — delete-then-recreate fires fresh because Sheets assigns a new sheetId per creation. Bounded payload — `{changeKind, spreadsheetId, worksheetId, worksheetName, index, sheetType}` only, no raw `sheets[]` spread.

V1 rot NOT ported across Google Sheets 2.3 (audit GS-R7 closed + new GS-R22–GS-R29 from plan §3): unbounded `googleSheetsRowSnapshot.rowHashes` (GS-R7 closed by bounded window), polling-only Sheets triggers (GS-R22 — V2 stays on Drive `files.watch` push), `hasHeaders` / `skipEmptyRows` / `requiredColumns` filter chrome (GS-R23 — downstream-filter composable), separate `google_sheets_trigger_new_row` / `..._updated_row` trigger types (GS-R24 — folded into one `row_changed` with `changeKinds` array per audit §7 §13), first-poll-establishes-baseline / "first poll miss" bug (GS-R25 — V2 activate seeds strictly), `previousValues` aspirational outputSchema field (GS-R26 — V2 ships placeholder honestly), `changedColumns` aspirational outputSchema field (GS-R27 — V2 doesn't ship the field at all), unbounded `googleSheetsWorksheetSnapshot` with per-sheetId entries (GS-R28 — V2 name-list-only snapshot), V1 `google_sheets_trigger_new_worksheet` polling chrome (GS-R29 — V2 rides Drive watch). `row_changed` Q4 session-side-effect idempotency for trigger events NOT threaded (deferred at the V2 engine level pending a broader slice — matches Sheets 2.1 + 2.2). Full V1 rot inventory + skip table: [`docs/slices/phase-2/google-sheets-2-3-triggers-outcomes.md`](./docs/slices/phase-2/google-sheets-2-3-triggers-outcomes.md) §§3 + 7.

### Microsoft Excel Phase 2 patterns: handler-internal headers, batch-folded `add_row`, positional vs stable-id triggers, no ExcelJS (Microsoft Excel parity)

Microsoft Excel Phase 2 closed the Slice 15 gap with 4 net-new actions + a batch-mode fold + 3 new polling triggers, all on top of the same OAuth + shared `microsoftExcelPollingHandler` stack. Four durable rules every future Excel action / wrapper / trigger MUST follow:

1. **Header-aware actions read headers handler-internal, not via a UI dynamic-field renderer.** `update_row` + `add_row` (batch mode) both fetch `usedRange` at execution time and resolve header names against the resulting row 1. The Phase 2 dynamic-field renderer is **explicitly deferred to Phase 3 UI work** (P-X1 acceptance). Unknown column names FAIL LOUDLY listing every offender — no silent skip, no synthetic header (V1's behavior in some code paths was to skip; V2 rejects). `update_row` also PATCHes the full merged row (existing values overlaid with the supplied updates) so untouched cells stay populated — V1's per-cell PATCH loop is NOT ported.
2. **`add_multiple_rows` is permanently folded into `add_row` `rows[]` mode.** There is **no** `microsoft-excel:add_multiple_rows` registry entry. The single `add_row` handler picks between `values` (single-row, backwards-compatible Slice 15) and `rows[]` (1..1000 batch) via the schema's XOR refine. Batch mode is fail-loud: > 1000 rows rejected at parse time before any Graph call, empty row objects rejected, all unknown column names across all rows reported in one error. **No silent chunking, no partial success** (V1's `addMultipleRows` chunked into 200-row batches and could partially succeed; V2 does exactly one range PATCH for the whole batch). Pattern mirrors Gmail 2.2's `advancedSearch → searchEmails` fold and Notion 2.1's `list_page_content → get_block_children` fold.
3. **`updated_row` is positional and noisy under inserts/deletes; use `updated_table_row` for stable identity.** `updated_row` keys its snapshot on the 1-based row index as a string — a mid-sheet insert or delete shifts subsequent rows and flags every shifted row as "updated" on the next poll. This is an **accepted limitation** (audit NPD-T, Marcus 2026-05-14) and is NOT guarded inside the handler. Workflow authors that need stable row identity use `updated_table_row` instead, which keys on Graph's stable `index` so neighbor mutations do NOT spuriously fire. `new_worksheet` semantics: renames look like `{ remove old name, add new name }` from Graph's `/worksheets` endpoint and fire **one** event with `payload.worksheetName === <new>`. All three new triggers seed their baseline at activation time and **throw** on seed failure (orchestrator wraps as `TRIGGER_REGISTRATION_FAILED`) — V1's swallowed snapshot-seed errors caused the first-poll-miss bug and are NOT ported.
4. **`create_workbook` remains deferred — no ExcelJS, no binary workbook generation in V2's bundle.** V1's `createWorkbook.ts` (370 LOC) does `require('exceljs')` CJS inside `.ts` and generates an empty XLSX in-process (R-Excel-3). Microsoft Graph has no native workbook-create endpoint that ships an empty XLSX file. The action is deferred until either (a) ExcelJS is explicitly accepted in V2's bundle (ops decision: weight + license review), (b) a Graph-native path is found, or (c) a server-side template-file pattern lands. Until then, workflows that need a fresh workbook upload a pre-built template via OneDrive and operate on it.

One single shared `microsoftExcelPollingHandler` covers all 5 Excel event types (`new_row`, `new_table_row`, `new_worksheet`, `updated_row`, `updated_table_row`) via its `canHandle` predicate. The four satellite trigger directories register **activation only** — they share the handler. This keeps the polling registry size O(providers) rather than O(eventTypes). Slice 15's `Files.ReadWrite` scope covers every parity action and trigger; **no scope widening to `Files.ReadWrite.All`** was needed (SharePoint / shared-with-me workbooks remain deferred until requested). Full V1 rot inventory + deferral table: [`docs/slices/parity/microsoft-excel-parity-outcomes.md`](./docs/slices/parity/microsoft-excel-parity-outcomes.md) §§3 + 6.

### Stripe Phase 2 patterns: typed-and-narrow, Idempotency-Key on POSTs only, single-page lists, finder 404 → found:false (Stripe 2.1)

Stripe Phase 2 closed the registered-action parity gap with 6 actions on top of Slice 11's `stripeRequest` + `flattenForStripe` + `refreshAndRetry` + Q4 idempotency stack. Six durable rules every future Stripe action / wrapper / e2e MUST follow:

1. **Typed schemas only — no raw Stripe payload passthrough.** Every action input is a strict Zod schema (`.strict()`). Lists, objects, and discriminated unions are typed (`lineItems: [{ priceId, quantity }]`, `metadata: Record<string, string>`, `afterCompletion: discriminatedUnion("type", [redirect, hosted_confirmation])`). V1's `JSON.parse` of `line_items` / `metadata` / `after_completion` / `automatic_tax` strings is REJECTED at parse time. No `parseInt(quantity) || 1` silent coercion — invalid values fail loud.
2. **`Idempotency-Key` on POSTs; absent on GETs.** All POST `create_*` actions send `Idempotency-Key: ${runId}:${nodeId}:stripe_action_<name>` via `buildIdempotencyKey`. The action-type suffix matches V1's existing wire-format convention so cutover safety holds (`stripe_action_create_checkout_session` / `stripe_action_create_payment_link` / `stripe_action_create_invoice` / `stripe_action_create_customer` / etc.). V2 ADDS the header on `create_payment_link` + `create_invoice` where V1 omitted it. GET / list / find actions do NOT send the header — Stripe rejects it on GET requests. Unit tests + e2e both assert the header is absent on GETs.
3. **Lists are single-page by default.** `get_payments` returns ONE page of charges; workflow authors compose a downstream loop on `output.nextCursor` (the last charge's id when `hasMore: true`, else `null`). NO auto-pagination, NO client-side filter loops (V1's `getPayments` fetched all then filtered by `status` client-side because Stripe doesn't accept `status` on `/v1/payment_intents` — V2 REJECTS that pattern; compose a downstream filter node instead). 4. **Finder actions return `{found: false, ...}` on 404 — non-404 errors propagate.** `find_subscription`, `find_payment_intent`, and the Slice 11 `find_customer` all catch `NotFoundError` from the wrapper layer and return `{found: false, subscription/paymentIntent/customer: null}` without throwing. "Find" is semantically allowed-to-return-zero. `Unauthorized401Error` and any other error still propagates to the engine — finders are NOT a global error-swallowing convention.
5. **Bounded output projections — no raw Stripe response spread.** Every Stripe handler builds output from a fixed key set off the Stripe wire response. No `...result` spread. Nulls are preserved where Stripe returns nullable fields. The `find_subscription` output projection deliberately omits the raw `items.data` array (use a future `get_subscription_items` if needed); `find_payment_intent` deliberately omits `client_secret` (confirm-time) and `next_action` (mid-flow). No "I'll just spread the rest of the response" escape hatch.
6. **Do NOT pre-port V1's 13 orphan handlers.** V1's `lib/workflows/actions/stripe/` carries 13 `.ts` files that are NOT in V1's `registry.ts` and NOT in V1's node defs — they're intentional dead code (`createInvoiceItem`, `createPrice`, `createProduct`, `updateInvoice`, `updateProduct`, `finalizeInvoice`, `voidInvoice`, `findCharge`, `findInvoice`, `listProducts`, `getCustomers`, plus `capturePaymentIntent` / `confirmPaymentIntent` which Slice 11 already shipped despite being V1 orphans). Per parity audit NPD-S1: "build new" decision, not "port" decision. `getCustomers` (bulk PII export) is permanently skipped pending an explicit product decision.

Airtable 2.1 closed the parity gap surfaced by [`docs/slices/parity/parity-airtable.md`](./docs/slices/parity/parity-airtable.md) with 3 net-new actions + 1 trigger discriminator fold + 1 field-type promotion. Six durable rules every future Airtable action / wrapper / trigger MUST follow:

1. **Batch actions use TRUE Airtable batch APIs — max 10, all-or-nothing, ONE wrapper call per invocation.** `create_multiple_records` posts to `/v0/{baseId}/{tableIdOrName}` with `body.records = [{fields}]`; `update_multiple_records` PATCHes the table endpoint with `body.records = [{id, fields}]`. 2. **Batch errors are all-or-nothing — no `continueOnError`, no partial-success envelope, no `success: false` synthetic ActionResult.** Airtable returns 422 if any record fails validation; the error propagates verbatim to the engine. **No per-record retry.** **No `failedRecords[]` / partial-success output.** V1's `continueOnError` config flag (A-R13) and V1's `success: false` synthetic envelope pattern (A-R15) are both rejected at audit time. Schema `.strict()` rejects `continueOnError`, `preserveExisting`, and `appendToExisting` at parse time so workflow authors can't silently re-enable the V1 shape.

3. **Attachment writes use the typed `[{url, filename?}]` shape OR `add_attachment` with a FileRef — never V1's heuristic or temp-upload.** `_shared/airtable/fields.ts` SUPPORTS `"attachment"` (Airtable 2.1 Commit 1 promotion). Byte ingestion uses the dedicated `add_attachment` action with a `FileRef`. **NO attachment-by-name heuristic** (V1's "if field name contains 'photo' it's an attachment" at `createRecord.ts:669-672` — A-R6 — is rejected; explicit `type: "attachment"` required). **NO Supabase temp-upload coupling** (V1's `supabaseAttachment.ts` 133-LOC helper — A-R7 — is replaced by P-S3).

4. **`add_attachment` rejects `FileRef(kind=provider_url)` at handler entry with `AirtableAddAttachmentConfigError`.** Mirrors Slack 2.4's `SlackUploadConfigError` pattern (per P-S3 durable rule #5). 5. **`table_deleted` is a `payload.eventType` discriminator inside `record_changed`, NOT a separate trigger type.** V1 ships THREE trigger types (`new_record` / `record_updated` / `table_deleted`). Slice 10 already folded V1's first two into a consolidated `record_changed` trigger with `eventType: created | updated | deleted | unknown`. Airtable 2.1 extends the same discriminator with `"table_deleted"` rather than introducing a fourth registry entry. Wire shape consumed: root-level `destroyedTableIds: string[]` on the webhook payload (Airtable's actual shape — destroyed tables live at the payload root, NOT inside `changedTablesById`, since the table no longer exists). One TriggerEvent per destroyed tableId. Dedup key shape: `${webhookId}:${tableId}:_table_:table_deleted:${baseTransactionNumber}`. Outer `TriggerEvent.eventType` stays `record_changed` so the `(provider, eventType)` dispatcher lookup uses the existing scope; workflows branch on `payload.eventType` for table_deleted-specific behavior. **NO `airtable:table_deleted` trigger registry entry was added.** V1's `destroyed_table_ids` snake_case alias is NOT ported (V2 trusts current Airtable's camelCase responses — A-R10 convention). V1's `watchedTables: string[]` config-side filter is NOT ported (workflows branch on `payload.tableId` downstream).

6. **Do NOT port V1 orphan handlers; do NOT add workflow-recipe actions as dedicated handlers.** V1's `moveRecord.ts` (129 LOC, NOT registered in V1's registry) is **permanently skipped** — workflow recipe equivalent: `get_record` → `create_record` in destination → `delete_record` in source. V1's `duplicateRecord.ts` (266 LOC, registered) is also **permanently skipped** as a workflow recipe — `get_record` → `create_record` with field overrides; V1's `fieldsToCopy` / `fieldsToOverride` structural mapping belongs in the builder UI / variable mapping (Phase 3), not a dedicated handler. Same rule as Stripe 2.1 §6 (V1 orphan backfill is on-demand, gated by product signal) and Notion 2.1 §2.1 (no router / no make_api_call / typed-and-narrow).

E2E regression guards. The Slice 10 walkthrough's added `2.1 parity` test pins five behaviors in one compressed test (~43s with `--workers=1`):

### Mailchimp Phase 2 patterns: single-page reads, PATCH-not-DELETE unsubscribe, M-R3 dead-flag rejection, baseline-first polling, stable-id snapshots (Mailchimp 2.1)

Mailchimp 2.1 closed the audit's accepted PORT set (4 actions + 3 polling triggers) on top of Slice 14's baseline (10 subscriber/audience/segment/note/event actions + consolidated `audience_event` webhook trigger with 6-event allowlist + 3 polling triggers + per-datacenter API-host routing + non-refreshable OAuth + Mailchimp-doesn't-sign-webhooks pattern). Zero new platform-tier work; zero new migrations; zero scope changes. Six durable rules every future Mailchimp action / wrapper / trigger MUST follow:

1. **Mailchimp read/list actions are single-page only.** `get_subscribers` + all 3 new polling triggers' activation + poll fetches return one page; count clamped at 100 in the wrapper (well below Mailchimp's 1000 server cap). No auto-pagination anywhere. Workflow authors compose pagination via the action's `nextOffset` output (for `get_subscribers`) or by structuring multiple workflows around segment / list state. The wrappers (`membersList`, `segmentMembersList`, `listsList`) return `{members | lists, totalItems}` so callers can derive "has more pages" without re-fetching. Reason: auto-pagination would either time out a single action invocation OR persist an unbounded snapshot that breaks JSONB equality. Both are explicit non-goals per audit §11 + §12 R3.

2. **`unsubscribe_subscriber` is PATCH `status: 'unsubscribed'` — NOT archive / delete.** Preserves the subscriber record. Distinct from Slice 14's `remove_subscriber` (Q11 destructive-gate `mode` field for archive vs hard-delete). Wire: `PATCH /3.0/lists/{listId}/members/{md5LowercaseEmail}` body `{status: 'unsubscribed'}`. Workflow authors who want to permanently delete a subscriber compose `remove_subscriber`. Authors who want to send a goodbye email — Mailchimp does NOT support this at the API; it's a list-level dashboard setting. Authors who want to attach a reason note compose `add_note` explicitly downstream.

3. **No hidden notification / note side effects on subscriber mutations.** V1's three dead flags (`sendGoodbye`, `sendNotification`, `reason`) are rejected at schema-parse time on `unsubscribe_subscriber` (`.strict()` Zod schema). The first two were TODO-only logs in V1; the third fired a hidden `POST /notes` call wrapped in `.catch(swallow)` — non-atomic, hidden side effect. V2 surfaces the rejection clearly so workflow authors discover the boundary at config time. The same pattern applies to future Mailchimp mutations: never silently fan out secondary API calls. Anti-test in e2e asserts the PATCH body has NO `sendGoodbye` / `sendNotification` / `reason` keys.

4. **Polling triggers baseline-first; never replay historical state.** Every polling-trigger activation hook (`subscriber_added_to_segment`, `segment_updated`, `new_audience`, plus Slice 14's `campaign_created`, `email_opened`, `link_clicked`) captures the current Mailchimp state into the trigger row's `config.snapshot` BEFORE the first poll runs. Activation throws `MissingDataCenterError` if dc is absent — trigger never registers. First poll after activation observes the same state and emits zero events. New entities on subsequent polls fire one event per new entity. This rule is asserted in 4 unit tests (one per polling-trigger type that ships) plus the e2e's parametrized "first tick after activation → 0 runs" assertion.

5. **Polling snapshots use stable provider IDs, not email-address snapshots where avoidable.** `subscriber_added_to_segment` snapshots store Mailchimp `member.id` values (md5(lowercase(email)) hashes), NOT raw email addresses. V1 used `email_address` in its snapshot map; V2 changes to `member.id` for two reasons: (a) privacy — raw emails persisted in JSONB snapshots become a quiet PII surface; the hash is opaque-looking and recoverable only by the Mailchimp API; (b) stability — the hash is what Mailchimp keys subscriber endpoints by; using it directly aligns the snapshot with the wire-format dedup discriminator. Set-based snapshots are stored as sorted arrays (stable JSONB equality) and grow monotonically (one-way diff — removal doesn't shrink the snapshot, so a member leaving + rejoining doesn't fire a duplicate event). `segment_updated` snapshots always overwrite to the latest observed state regardless of whether the poll fired (closes the loop on idle ticks).

6. **`create_campaign` / `send_campaign` / `schedule_campaign` remain out of 2.1.** Email sending is high-blast-radius — a single workflow run can send to every audience subscriber. NPD-M1 (d) reserves `create_campaign` only for Mailchimp 2.2 under a Q11 explicit-consent contract (and an NPD-M3 Q4 idempotency bracket spanning the campaign's two API calls); `send_campaign` and `schedule_campaign` stay deferred indefinitely on blast-radius grounds. **Do NOT add either action without a fresh Marcus signoff.** Workflow authors who need campaign creation today must use the Mailchimp dashboard.

V1 rot NOT ported across Mailchimp 2.1: M-R3 (`sendGoodbye` / `sendNotification` flags + the `reason` hidden-`/notes` extension — all dropped at schema parse), M-R4 + M-R7 + M-R11 (campaign-create defaults — deferred to 2.2 along with the action itself), M-R6 (no Q11 guard on `sendCampaign` — deferred indefinitely with the action), M-R10 (two-call campaign-create non-atomicity — reserved for 2.2 under NPD-M3 (a) Q4 bracket). Mailchimp 2.1 Q4 session-side-effect idempotency NOT threaded — deferred at the V2 engine level pending a broader slice (matches Slice 13 + 14 + Sheets 2.1/2.2/2.3 + Stripe 2.1 + Airtable 2.1 + Shopify 2.1 + HubSpot 2.1). Full V1 rot inventory + closure / deferral table: [`docs/slices/parity/mailchimp-2-1-outcomes.md`](./docs/slices/parity/mailchimp-2-1-outcomes.md) §4.

### Microsoft Outlook Mail Phase 2 patterns: Mail.ReadWrite scope, Q11 replyAll/isHtml/importance, parseRecipients on forward + draft, FileRef[] send attachments, fileAttachment-only, no bytes in outputs (Outlook Mail 2.1)

Outlook Mail 2.1 closed the Compose & Drafts batch (3 net-new actions + `send_email` attachment expansion + P-O1 manifest widening) on top of Slice 6's baseline (1 action + `new_email` subscription-watch trigger + per-trigger lifecycle directory + validation-handshake + clientState verification). Zero new platform-tier work; zero new migrations; one new generic service helper (`createWorkflowFilesStorageAdapter`). Seven durable rules every future Outlook Mail action / wrapper / handler MUST follow:

1. **Outlook Mail requires `Mail.ReadWrite` for drafts + lifecycle actions; existing accounts reconnect through proactive-health.** Manifest is `["offline_access", "Mail.Send", "Mail.Read", "Mail.ReadWrite"]` — 4 required scopes, no optional. `Mail.ReadWrite` is REQUIRED (not demoted to optional) so a workflow author whose account granted only the older 3-scope set discovers the gap via a clean Graph 403 → `action_required` → standard OAuth reconnect, NOT a silent partial-grant. **No migration script — the proactive-health system handles the re-auth flow.** Mail.ReadWrite is a superset of Mail.Read; both declared so an IT-restricted tenant granting only the narrower scope can still run `send_email` + `new_email`. **Do NOT add Calendar / Files / Teams / Contacts scopes** to this manifest — that's V1's R3 9-scope mega-list rot; sibling Microsoft providers own their own scope-narrowed manifests. The e2e walkthrough pins the 4-scope authorize-call assertion — any drift fails CI.

2. **Q11 explicit-required on 3 fields; no hidden defaults.** Every compose/draft handler schema enforces:
   - `reply_to_email.replyAll`: REQUIRED boolean. No default. Endpoint switches on this (`/me/messages/{id}/reply` vs `/replyAll`) — silent defaulting would send a narrower or broader message than the workflow author intended.
   - `create_draft_email.isHtml`: REQUIRED boolean. V1 silently defaulted to `false`.
   - `create_draft_email.importance`: REQUIRED enum (`"low" | "normal" | "high"`). V1 silently defaulted to `"normal"`; "high" sets the Outlook flag/exclamation visible in the recipient's inbox.
   `send_email` ships the same 2 Q11-required fields (`isHtml`, `importance`) per Slice 6 baseline. **Any new Outlook handler with a destructive or recipient-visible behavior toggle MUST be Q11-required** — never silently default.

3. **`parseRecipients` (Q7) routes every multi-recipient field across the Outlook handler set.** `send_email.to`/`cc`/`bcc`, `forward_email.to`/`cc`, `create_draft_email.to`/`cc`/`bcc` ALL flow through `core/integrations/parseRecipients.ts`. CSV strings split, arrays flatten, empties drop. **At-least-one parsed `to` recipient is enforced AFTER parsing in each handler** — the schema's `.min(1)` catches "no value at all" but not whitespace-only CSVs like `"   ,   "`, so the post-parse check fires a clean handler error. This closes V1's O-R3 rot end-to-end: V1's `forwardOutlookEmail` passed CSV strings verbatim, Graph treated the whole CSV as one address. **Never pass raw user-supplied recipient strings directly to Graph.**

4. **`send_email` attachments are FileRef[] only; `provider_url` REJECTED at handler entry.** Schema field is `attachments?: z.array(FileRefSchema).optional()` — `FileRefSchema` strict-arms reject any inline-bytes shape (`content`, `bytes`, `base64`, `data`) at parse time so raw bytes NEVER reach the handler. Per-kind dispatch:
   - **`signed_url`**: direct `fetch(url)` via `core/files/fetchFileBytes.ts` (no auth header). Storage adapter NOT constructed.
   - **`v2_storage`**: workflow-files storage adapter constructed LAZILY via `services/files/createWorkflowFilesStorageAdapter.ts`; threaded into `fetchFileBytes(ref, { storage })`. Adapter creation happens only when at least one FileRef has `kind === "v2_storage"`.
   - **`provider_url`**: handler short-circuits BEFORE any byte fetch — throws `UnsupportedProviderFetchError(provider)`. No Graph call, no token decrypt, no storage adapter constructed. P-S3 plan §10 #1 message verbatim. **Workflow authors who need to attach a provider-issued URL stage it through `stageFileToStorage` first** (Slack 2.4 `download_file` is the canonical producer).

5. **`send_email` attachment size caps are HARD, 3 MB per / 25 MB total.** Constants in the handler: `MAX_ATTACHMENT_SIZE_BYTES = 3 * 1024 * 1024`, `MAX_TOTAL_ATTACHMENT_SIZE_BYTES = 25 * 1024 * 1024`. Caps checked AFTER byte fetch but BEFORE base64 encoding + the wrapper call — so failures don't burn a Graph 401-retry cycle. Per-attachment error reports the attachment name + observed byte count; total-cap error reports total bytes. **Microsoft Graph's upload-session flow (`POST /me/messages/{id}/attachments/createUploadSession`) is deferred** — handler fails loud rather than implementing the multi-step protocol. Re-revisit only if a workflow concretely needs > 3 MB single or > 25 MB total in one send.

6. **P-O2 — `fileAttachment` PORT ONLY; `itemAttachment` + `referenceAttachment` SKIP.** Outlook Mail 2.1 send-side ports only the `#microsoft.graph.fileAttachment` subtype. `itemAttachment` (embedded message / event) and `referenceAttachment` (OneDrive / SharePoint link) are SKIPPED both because the FileRef contract has no clean shape for nested-protocol payloads AND because `referenceAttachment` resolution would require a separate provider call. **The receive-side `get_attachment` action (Outlook Mail 2.3) MUST inherit the same SKIP boundary** — only `fileAttachment` materializes to bytes; the other two return metadata-only with `skipped: true`. Re-revisit only if a workflow concretely needs forwarded embedded messages OR OneDrive-linked attachments.

7. **No bytes / base64 / content in any Outlook action output.** `send_email` output is unchanged across 2.1 — the same 7-field shape (`sent`, `to`, `cc`, `bcc`, `subject`, `isHtml`, `importance`). NO `attachments`, NO `contentBytes`, NO `base64`, NO `bytes`, NO FileRef echoed. CLAUDE.md rule #1 enforced at both layers: unit tests assert at the handler boundary; e2e reads `workflow_runs.steps[i].output` directly and asserts the same. **Future Outlook handlers (`get_attachment` in 2.3, etc.) MUST stage bytes through `stageFileToStorage` and return FileRef[] — never base64 / Buffer / raw bytes in action outputs.** The `createWorkflowFilesStorageAdapter` helper is the reusable consumer primitive; pair it with `stageFileToStorage` for produce-then-consume chains.

V1 rot NOT ported across Outlook Mail 2.1: V1's 741-LOC `emailActions.ts` monolith holding 8 handlers + the `searchOutlookEmail` orphan (registry test pins the 4-action set; orphan never registered); V1's 9-scope Microsoft mega-list (Slice 6 + P-O1 widening keep manifest narrow); V1's `replyToOutlookEmail.replyAll = false` hidden default + `createOutlookDraftEmail.importance = "normal"` hidden default (both Q11-required); V1's `forwardOutlookEmail` CSV-passes-as-one-address bug (Q7 parseRecipients closes O-R3); V1's `forwardOutlookEmail.comment = ""` hard-default (V2 omits when absent); V1's 5-source-type sendEmail attachment model (replaced by FileRef[]); V1's `MicrosoftGraphSubscriptionManager` empty-accessToken renewal bug (closed at Slice 6 via `refreshAndRetry` in `renew.ts`); V1's inline `getDecryptedAccessToken` + `refreshMicrosoftToken` per-handler pattern (closed by V2's central `refreshAndRetry`). Outlook Mail 2.1 Q4 session-side-effect idempotency NOT threaded — deferred at the V2 engine level pending a broader slice (matches Slice 6 + Slice 13 + Slice 14 + Sheets 2.1/2.2/2.3 + Stripe 2.1 + Airtable 2.1 + Shopify 2.1 + HubSpot 2.1 + Mailchimp 2.1). Full V1 rot inventory + closure / deferral table: [`docs/slices/parity/outlook-mail-2-1-outcomes.md`](./docs/slices/parity/outlook-mail-2-1-outcomes.md) §4.

### File output contract (P-S3)

V2 ships a strict file-output contract. Full design + 10 numbered security rules: [`docs/slices/phase-1/p-s3-file-output-contract-outcomes.md`](./docs/slices/phase-1/p-s3-file-output-contract-outcomes.md). Six durable rules every future provider / handler / repository / service must follow:

1. **Action outputs never carry raw file bytes or base64.** No `content`, `bytes`, `base64`, or `data` keys for file content. The Zod `FileRefSchema` is `.strict()` per arm — those keys are rejected at parse time. The runs table is the audit/debug surface; it MUST stay free of binary blobs.
2. **File-like outputs use `FileRef`.** Constructed via the builders in [`core/files/createFileRef.ts`](./core/files/createFileRef.ts) (`fileRefFromProviderUrl`, `fileRefFromStoragePath`, `fileRefFromSignedUrl`), never as object literals. `FileRefKind` is closed: `"provider_url"`, `"v2_storage"`, `"signed_url"`. No inline arm — there is no `kind` value that legitimizes inline bytes.
3. **Download actions stage durable bytes to `v2_storage`** via [`services/files/stageFileToStorage.ts`](./services/files/stageFileToStorage.ts) unless they are intentionally returning metadata-only (`provider_url` for unchanged provider URLs, `signed_url` for auth-free links). Staging is the default because the runs table outlives provider URL TTLs and cross-provider chains need durable bytes.
4. **Repositories stay metadata-only; Supabase storage access lives in `services/files/`.** [`repositories/workflowFiles.ts`](./repositories/workflowFiles.ts) does CRUD over `public.workflow_files` rows and nothing else — zero `supabase.storage.*` access. The Commit 3 `storage isolation invariant` test enforces this with a mock client whose `.storage` field is `undefined`. New file flows put their object I/O in `services/files/`.
5. **`provider_url` fetching requires explicit provider-safe auth handling.** [`core/files/fetchFileBytes.ts`](./core/files/fetchFileBytes.ts) deliberately throws `UnsupportedProviderFetchError` for `kind=provider_url`. Per-provider helpers land alongside the consumer slice (Slack 2.4 download is the first). Do NOT implement a generic "fetch any provider URL with whatever token I can find" path — token lookup, scope checking, and refresh handling are provider-specific.
6. **The cleanup cron response is counts-only.** [`/api/cron/cleanup-workflow-files`](./app/api/cron/cleanup-workflow-files/route.ts) MUST NOT expose row ids, storage paths, or user ids — cron monitors are operational surfaces that would otherwise leak workflow / user metadata. The response shape is `{ ok, scanned, storageDeleted, metadataDeleted, failed, startedAt }`; the route test diffs JSON keys against this set.

**Companion rules (also covered in the outcomes doc):**

- The `workflow-files` Supabase storage bucket is created **out-of-band** (ops); SQL migrations do not poke at `storage.buckets`. The bucket name + path scheme `<userId>/<workflowId>/<runId>/<nodeId>/<filename>` are pinned in [`core/files/fetchFileBytes.ts::WORKFLOW_FILES_BUCKET`](./core/files/fetchFileBytes.ts) and the migration header.
- `signed_url` refs are bearer-equivalent secrets. Producers MUST set `expiresAt` when the lifetime is known. The URL never appears in logs or error messages — `fetchFileBytes` strips it from `FileFetchError`.
- Filenames are sanitized via [`core/files/sanitizeFilename.ts`](./core/files/sanitizeFilename.ts) before any storage path or provider API use. Always.
- Per-provider size guidance ([`core/files/limits.ts`](./core/files/limits.ts)) is **advisory** — Phase 7 will add hard quotas. Stage warns when exceeded but does not reject.

### Native control-flow patterns: pure handlers over engine `branchTaken`, strict equality, no regex/eval/JS expressions (Native Slice 3)

Native Slice 3 shipped the two Tier C control-flow actions (`if_then_condition`, `router`) as pure handlers over the engine-branching contract (`WorkflowEdge.label?`, `ActionHandlerResult.branchTaken?`, `selectActivatedEdges`, `status: "skipped"`, `INVALID_BRANCH`). Full design + 15 numbered decisions: [`docs/slices/parity/native-nodes-3-tier-c-control-flow-outcomes.md`](./docs/slices/parity/native-nodes-3-tier-c-control-flow-outcomes.md). Eight durable rules every future control-flow or branching handler MUST follow:

1. **Both actions are pure handlers over `{output, branchTaken}` — the engine owns selection, skip propagation, INVALID_BRANCH, persistence, and notification.** Slice 3 added zero engine code; the entire control-flow surface is two action files + their schemas + a shared 200-LOC evaluator. New control-flow patterns (multi-condition, weighted router, etc.) MUST also be pure handlers over the same return shape — don't add another engine code path until a real workflow proves the seam insufficient.

2. **`if_then_condition` emits `branchTaken: "true" | "false" | null`.** True → `"true"`. False AND `onFalse: "branch"` (default) → `"false"`. False AND `onFalse: "skip"` → `null`. **Author-facing rule:** if you wire only a `"true"` outgoing edge, set `onFalse: "skip"` to avoid `INVALID_BRANCH` on the false path. This is THE most common slip — the Slice 3 e2e walkthrough has a dedicated scenario pinning it.

3. **`router` uses first-match-wins over `routes[]` in declaration order; emits matched route's `label`, else `defaultRoute`, else `null`.** Max 32 routes; route labels min 1 / max 64 chars and must be unique. No magic `"Else"` string — author names the default label via `defaultRoute`; engine `INVALID_BRANCH` catches missing wiring. `null` (no match + no `defaultRoute`) is the documented "skip all labeled outgoing edges" signal; unlabeled cleanup edges still activate.

4. **Both actions share the 14-operator pure evaluator at [`integrations/native/actions/_conditionEvaluator.ts`](./integrations/native/actions/_conditionEvaluator.ts).** Operators: `equals`, `not_equals`, `contains`, `not_contains`, `starts_with`, `ends_with`, `greater_than`, `less_than`, `greater_equal`, `less_equal`, `is_empty`, `is_not_empty`, `is_truthy`, `is_falsy`. **Strict `===` for equality** (departs from V1 `==`); **case-insensitive for string operators** (V1 parity); **narrowed numeric coercion** (only `number` and non-empty trimmed numeric strings coerce — `null`/`bool`/`array`/`object`/empty/whitespace/`NaN`/`Infinity` never coerce); **operator/type mismatch returns `false` defensively** (no runtime throws — only Zod schema-parse failures throw, which the engine converts to `HANDLER_FAILED`).

5. **No `eval`, no `new Function(...)`, no regex literals, no `new RegExp(...)`, no logger, no `node:fs` / `node:http` / `node:https` imports, no `console.*` calls.** Enforced by 5 source-purity guards in `conditionEvaluator.test.ts` that read the source at test time, strip comments, and assert the runtime code is free of these primitives. **Permanent skip on regex** (ReDoS surface — revisit only behind a bounded regex executor) and **permanent skip on JS-expression mode** (security + determinism). A future contributor who reaches for any of these breaks the build before integration tests notice.

6. **No multi-condition AND/OR in a single node.** Single condition per `if_then_condition`; single condition per route in `router`. Workflow authors compose AND via chained `if_then_condition` nodes (`true` → next condition) and OR via `router` with multiple routes (the OR-arms). The schema stays small; the handler stays a one-liner against the shared evaluator. **Rule:** if a multi-condition node ever becomes necessary, ship it as a NEW `native:multi_condition` action with its own schema — don't reopen `if_then_condition.schema.ts`.

7. **Outputs are bounded — no echo of `input` or `value`.** `if_then_condition` output is exactly `{ conditionMet, operator, onFalse }`. `router` output is exactly `{ matched, routeLabel, evaluatedCount }`. Keeps `workflow_runs.steps[].output` free of potentially-large or sensitive payloads. The router e2e test asserts `JSON.stringify(output)` does NOT contain a planted secret-string. **Rule for future control-flow actions:** output schema is fixed scalars; no `input` / `value` / config echo.

8. **Edge-label convention is part of the contract.** `if_then_condition`: `"true"` / `"false"` (optional) / unlabeled cleanup (optional). `router`: every `routes[].label` + optional `defaultRoute` + optional unlabeled cleanup. Engine `INVALID_BRANCH` is the safety net for missing wiring. Skipped branch nodes emit `RunStepResult { status: "skipped" }` with `output: undefined` — they do NOT call the handler, do NOT call the resolver, and do NOT write `variables[id]`. Downstream nodes that reference a skipped node's output fail naturally with the engine's `MISSING_VARIABLE` step.

V1 rot NOT ported across Native Slice 3: V1's duplicate `executePath.ts` + `executeFilter.ts` orphans (NPD-N10 PERMANENT SKIP — V2 ships exactly one `if_then_condition` implementation); V1's `executeRouter.ts` `selectedPathId` bespoke protocol (V2 uses `branchTaken` over the standard engine contract); V1's magic `"Else"` no-match string (replaced by author-configured `defaultRoute`); V1's `mode: "filter" \| "router"` config split (V2 router has one mode; filter semantics rebuild via `defaultRoute` omission + unlabeled cleanup); V1's `continueOnFalse: boolean` field (subsumed by `onFalse: "skip"` + unlabeled outgoing edges); V1's `conditionType: "simple" \| "multiple" \| "advanced"` selector (`"multiple"` deferred per D-IT4; `"advanced"` JS-expression mode PERMANENT SKIP); V1's loose `==` cross-type coercion (V2 strict `===`); V1's `Number(null)=0` / `Number(true)=1` / `Number([7])=7` silent coercion (V2 narrowed); V1's per-evaluation `logger.info` / `logger.error` calls (V2 native handlers emit zero logs); V1's `{success, error, message}` envelope on failure (V2 throws → engine `HANDLER_FAILED`). Full V1 rot inventory + closure / deferral table: [`docs/slices/parity/native-nodes-3-tier-c-control-flow-outcomes.md`](./docs/slices/parity/native-nodes-3-tier-c-control-flow-outcomes.md) §4.
